Building Dynamic RBAC with Entra ID & User-Level Permission Overrides

Lessons from a Real System

The problem with if user.role == "admin"

Most RBAC implementations start the same way: an enum. employee, manager, admin. It's fast to ship, easy to reason about, and it works — right up until someone asks for a fourth role, or a fifth, or "can we give Priya everything a compliance officer has, plus the ability to edit wiring lookup tables, without making her a compliance officer?" A hardcoded enum can't answer that question without a code deploy. That's the wall every growing RBAC system eventually hits, and it's the one worth designing around from day one if you can.

Here's how I approached it building out RBAC for a highly regulated Corporate Treasury Management Platform on top of Microsoft Entra ID (Azure AD) — including a few mistakes and a real security incident that shaped the final design.

Start from the data model, not the enum

The core shift is treating roles as rows, not values. Three tables carry the whole system:

  • roles — id, name, is_system (protects the seeded baseline roles from rename/delete), is_default (which role a user falls back to if nothing else claims them).
  • permissions — a flat catalog of fine-grained capability codes (transaction.view.own, transaction.view.department, transaction.approve_bulk, user.manage, role.manage, and so on — deliberately granular, not one blob permission per feature).
  • role_permissions — a many-to-many join: which permissions each role grants by default.

None of this is novel — it's the standard RBAC shape. The part that actually matters is what you do on top of it.

The override layer: don't make people abuse roles to grant one permission

The moment you have real roles, you get a real request: "give this one treasury analyst the ability to bulk-approve low-value transactions, but don't make them a manager." If your only lever is role, you're stuck cloning roles for one-off exceptions — which is how you end up with manager, manager-but-no-approve, manager-2 six months later.

The fix is a fourth table: per-user permission overrides, each one a (user, permission, effect) triple where effect is grant or revoke. A user's actual permission set becomes:

role defaults ∪ overrides(grant) − overrides(revoke)

resolved fresh for every login. This one addition means the role table stays clean — roles describe the common case, overrides describe the exception — and nobody's tempted to fork a new role just to hand one person one extra permission.

Wiring it to Entra: group claims, not hardcoded config

The Entra side of this is a single mapping table: idp_group → role. On login, you read the groups claim off the ID token, look up which role(s) map to those group names, and assign the role. The two decisions that matter here:

  • Make the mapping admin-editable, not config. The naive version is an env var: OIDC_ADMIN_GROUPS=Group-A,Group-B. That means every new Entra group requires a deploy. Putting it in a table means an IT admin can wire up a new Entra security group to an existing role from the admin UI, same afternoon it's created in Azure.
  • Treat ambiguity as an error, not a puzzle to solve. If a user's Entra groups map to two different roles, don't silently pick one — reject the login with a clear error. Silently resolving it (e.g., "highest privilege wins") just means a misconfigured group mapping fails open instead of loud, and nobody notices until it matters.

There's a second wrinkle worth designing for: manual overrides need to survive IdP sync. If an admin manually bumps someone's role in the app, and that person's Entra groups haven't changed, the next login shouldn't silently revert it. The fix is a role_source flag (idp vs. manual) — IdP-driven sync only touches accounts still flagged idp; a manual change flips that flag and sticks until an admin explicitly reverts it.

Make permission checks free

Resolving a user's full permission set is a handful of joins — cheap once, expensive if you do it on every request. So don't: resolve it once, at login, and bake the result straight into the JWT. Every subsequent request checks permission in token.perms — a list membership test, zero database round trips.

The catch: a JWT is a bearer token good until it expires. If an admin revokes a permission, or deactivates someone, or changes their role, the old token is still valid until it naturally times out — unless you account for it. The fix is a monotonic token_version stamped into every issued token. Bump the user's token_version on any permission-relevant change (role edit, deactivation, explicit logout), and check it on every request: a token issued before the current version is rejected outright, even though its signature is still perfectly valid. That's what turns "your access was just revoked" into an immediate fact instead of a 30-minute-token-expiry-later fact.

The escape hatches you can't fully avoid — and how to contain them

Purism says every authorization decision should route through the permission system, with zero hardcoded role names anywhere in the codebase. In practice, a system needs at least one break-glass path that works before the permission system can even be trusted — a bootstrap admin account for first boot, a local login path that has to work even if Entra itself is down or misconfigured. Those paths, by necessity, check a literal role name rather than a permission code, because they exist to get you into the system that assigns permissions in the first place.

The honest move isn't to pretend you can eliminate these — it's to name them, document them explicitly as the sanctioned exceptions, and keep the list as short as possible. In this system that's exactly two things: the seed script that creates the very first account, and the local login gate that checks for it. Everything else — every feature, every admin action — goes through the permission system, no exceptions.

The war story: adding a top-tier role taught me where the real boundary lives

The most useful lesson came from a mistake. I added a new top-tier role — let's call it Super Admin — to hold one especially sensitive permission (SSO/Entra configuration itself) exclusively, deliberately unreachable via Entra group mapping, reachable only through that one break-glass local login. The login gate was updated to check for it. Looked airtight.

It wasn't. I ran a focused security review before shipping, and it surfaced something I'd missed: the login gate was the only place I'd added the restriction. The existing "create a local account" and "edit a user's role" endpoints — both already gated behind a much more common, much more widely-held permission — had no idea the new role was supposed to be exclusive. Anyone holding that ordinary permission could just assign themselves the new top-tier role through a completely unrelated form, then log in through the gate that was supposedly guarding it. The gate was solid; the door next to it was wide open.

The fix, and the actual lesson: a privilege boundary has to be enforced everywhere a role gets attached to an account, not just at the one endpoint you were thinking about when you drew the boundary. That meant walking every code path that assigns a role — account creation, profile edits, the Entra-mapping admin UI — and adding one shared guard, rather than trusting that a single checkpoint downstream would catch what upstream code let through. If I were doing it again, I'd draw that map — every place a role gets assigned — before writing the new role, not after a review found the gap.

Takeaways

  • Roles are data, not code. The moment "add a role" requires a deploy, you're already behind.
  • Give yourself an override layer. Roles model the common case; per-user grant/revoke handles the exception, so nobody forks a role just to patch one person's access.
  • Admin-editable IdP mapping, and fail loud on ambiguity. Silent "pick a winner" logic on conflicting group mappings is a bug waiting to be invisible.
  • Bake permissions into the token, invalidate by version, not by waiting. Free reads, immediate revocation — you can have both.
  • Name your escape hatches on purpose, and keep the list short. Every hardcoded role check should be a deliberate, documented exception, not something that crept in.
  • A permission boundary is only as strong as its least-guarded entry point. Before shipping a new privilege tier, map every path that can assign a role to an account — not just the one you're actively building.
